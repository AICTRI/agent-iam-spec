# Agent IAM Series — Part 2: Registration and Discovery

- Series identifier: `agent-iam-series`
- Part identifier: `agent-iam-2-registration-discovery`
- Version: `0.1.0-draft`
- Date: 2026-09-22
- Status: Project draft, not an international, national, or industry standard
- License: CC BY 4.0 (specification text)

This part defines Agent naming, identity records, lifecycle, the registry, and identity discovery. It is the foundation for authentication (Part 3) and authorization (Part 4).

## 1. Scope

This part specifies:

- the Authority Namespace hierarchy and the identifier layers;
- the identity object model: Agent Identity Record, Agent Class, Authority Binding, Agent Blueprint, Workload Registration, and Agent Instance;
- the Agent and Instance lifecycle state machines and their invariants;
- the registry: registration transactions, uniqueness, and management-plane requirements;
- discovery: resolving a Namespace or Agent Identifier to trusted issuer metadata, keys, and trust bundles.

The capability, tool, and business-resource catalogs, and capability discovery, are out of scope.

## 2. Normative References

- Part 1 defines terms, trusted-data-source rules, fail-closed behavior, canonicalization, and revocation freshness vocabulary.
- Part 6 defines the security event envelope used for registration, lifecycle, and discovery events.

## 3. Terms

In addition to the terms in Part 1:

### 3.1 Registry

The authoritative store of Agent records, Authority Bindings, Workload Registrations, Instances, and lifecycle state for one or more Authority Namespaces. A registry is an identity authority.

### 3.2 Discovery Document

A signed or HTTPS-protected document published under an Authority Namespace that advertises the issuing authority, registry endpoint, verification keys, supported profiles, and federation trust configuration.

## 4. Identifier Specification

### 4.1 Identifier Layers

This part distinguishes four kinds of identifiers:

| Identifier | Scope | Example | Use |
|---|---|---|---|
| Authority Namespace | global, delegable | `https://id.example.com/org/acme` | naming and addressing of organizations/partners and internal divisions |
| Local Agent ID | within an Authority Namespace | `agt_01J...` | database primary identifier, API path |
| Cross-domain Agent Principal Key | issuer scope | `(iss, sub)` | Token, federation, audit |
| Workload ID | within trust domain | `spiffe://example.org/ns/a/sa/b` | runtime instance attestation |

### 4.2 Local Agent ID

The local Agent ID:

- MUST be generated by the identity authority;
- MUST be unique within its Authority Namespace;
- MUST be an opaque value; consumers MUST NOT parse business meaning from it;
- MUST NOT be modified after creation;
- MUST NOT be reused after the Agent is revoked;
- MUST NOT contain personal names, email addresses, organization names, or other unnecessary personal information;
- MUST provide an identifier space of at least 128 bits and sufficient collision security; when exposure of the identifier would create an enumeration risk, it MUST also have sufficient unpredictability. When a UUID is used, an appropriate version defined by RFC 9562 SHOULD be chosen.

`agt_<opaque-id>` is the recommended local representation of this series and is not a registered international URI scheme.

### 4.3 Global Uniqueness

Across namespaces or organizations, a bare `agent_id` does not have global uniqueness. A cross-domain principal key MUST be determined by the `(issuer, subject)` tuple. The issuer MUST resolve to an Authority Namespace, so `(issuer, subject)` is equivalent to `(Authority Namespace, Agent Subject)`; a Namespace may contain organization-internal division levels, but all levels MUST jointly form a single stable canonical value. At registration, the issuer MUST form a stable canonical value; at token verification, an exact string comparison MUST be performed against that registered value, and different issuers MUST NOT be collapsed through URI normalization during the verification phase. The subject MUST be unique under that issuer and MUST never be reassigned. The `iss_sub` of RFC 9493 can serve as a structured representation of this tuple:

```json
{
  "format": "iss_sub",
  "iss": "https://id.example.com/org/acme",
  "sub": "agt_01JABCDEF..."
}
```

When a URI representation is needed, an HTTPS namespace controlled by the deployer SHOULD be used, for example:

```text
https://id.example.com/org/acme/agents/agt_01JABCDEF...
```

Implementations MUST NOT invent unregistered URI schemes and claim that they have international interoperability.

### 4.4 Namespace Hierarchy

To support interactions between an enterprise and the Agents of its customers, partners, and suppliers, identifiers SHOULD be organized in the following hierarchy:

```text
Authority Namespace (principal-controlled root, globally unique, delegable)
  └─ organization-internal divisions (0..n sub-namespace levels)
       └─ logical Agent ID (unique within that Namespace)
            └─ Agent Instance (logical instance)
```

- An Authority Namespace MUST be globally unique and delegable, and MUST NOT be reassigned;
- organization-internal divisions MUST be expressed as sub-namespaces and MUST follow a single canonical rule;
- a local Agent ID MUST be unique within its Authority Namespace and MUST NOT be assumed unique across Namespaces;
- multiple organizations onboarded to the same deployment MUST each own an Authority Namespace and MUST NOT share or override one another;
- federation MUST preserve both parties' Authority Namespaces and maintain principal isolation per Part 5.

### 4.5 Relationship with SPIFFE ID

A SPIFFE ID identifies a workload within a trust domain. A logical Agent ID and a SPIFFE ID may establish a one-to-many or multi-generation binding, but MUST NOT be equal by default:

```text
Agent Identity 1 --- n Agent Instance 1 --- 1 current Workload Identity
```

Only when a deployment explicitly guarantees that the Agent and Workload lifecycles are exactly identical and does not need an independent Authority Binding, Agent epoch, or instance history MAY the same URI be reused; this simplification is not a recommended mode of this series.

### 4.6 National Identity Code and External Identifiers

If a deployment needs to be compatible with the agent identity code of `GB/Z 185.2-2026`, it SHOULD store it as an external identifier with a namespace and issuing authority, and MUST NOT override the local Agent Identity solely on the basis of an external code:

```json
{
  "type": "gbz185_identity_code",
  "issuer": "<verified issuing authority>",
  "value": "<identity code>"
}
```

The creation, change, and disassociation of an external identifier MUST produce audit events and MUST undergo authenticity verification by the issuing authority.

## 5. Identity Object Model

### 5.1 Agent Identity Record

The minimal record SHOULD contain:

```text
namespace
agent_id
agent_class
blueprint_id and blueprint_version, if used
authority_binding_ref
sponsor_ref, optional
lifecycle_state
lifecycle_epoch
created_at
updated_at
```

`namespace + agent_id` MUST be unique and is the uniqueness basis. Registering an Agent, creating an Authority Binding, and recording registration evidence SHOULD be committed in the same transaction.

### 5.2 Agent Class

This series defines:

| Class | Authority Root | Constraint |
|---|---|---|
| `twin` | `human_master` | exactly one immutable human master |
| `service` | `organization_root` | MUST NOT forge or carry a human master |
| `ephemeral` | `human_master` or explicitly specified by the deployment Profile | MUST have a short lifetime and an explicit expiry policy |

A deployment that does not support `ephemeral` MUST reject rather than degrade to `twin` or `service`.

### 5.3 Authority Binding

Every Agent MUST have exactly one Authority Binding. An Authority Root change MUST NOT be updated in place; the system MUST revoke the old Agent ID and create a new Agent Identity.

### 5.4 Agent Blueprint

If a Blueprint is used, it MUST be versioned and have determinable states such as `draft`, `published`, and `deprecated`. At registration, the same explicit version MUST be validated and persisted; it MUST NOT validate the "latest version" and then store a different version supplied by the caller.

### 5.5 Workload Registration

A Workload Registration MUST contain at least:

```text
namespace
workload_registration_id
platform
selector
trust_domain
allowed_proof_methods
status
```

The trust domain MUST be pre-associated with the same Authority Namespace. All storage implementations, including test or in-memory implementations, SHOULD enforce the same namespace/trust-domain constraint.

### 5.6 Agent Instance

An Agent Instance MUST contain at least:

```text
namespace
instance_id
agent_id
workload_registration_id
workload_id
artifact_digest, optional
attestation_ref
credential_generation
lease_expires_at, optional
instance_state
```

`attestation_ref` MUST be able to correlate to an actual verification result, and MUST NOT be merely declared in the schema without being written. The enrollment and attestation procedures that populate these fields are specified in Part 3.

## 6. Lifecycle

### 6.1 Agent State Machine

This series adopts:

```text
registered -> enrolled -> active -> suspended
     |           |          |          |
     +-----------+----------+----------+-> revoked

suspended -> enrolled -> active
revoked   -> no transition
```

An implementation may keep an internal `draft` state but MUST NOT issue usable identity credentials or execution authorizations for it.

### 6.2 Lifecycle Invariants

- Every legal state transition MUST atomically and strictly increase `lifecycle_epoch`;
- the epoch MUST NOT roll back or be reused;
- `revoked` MUST be terminal;
- only an `active` local Agent may obtain a new identity token or Execution Grant; a Federated/Brokered Principal without a local Agent record MUST obtain an Execution Grant only after an active Federation Trust, PoP, and authoritative online verification per Part 5;
- a `suspended` Agent MUST complete the required enrollment or equivalent re-verification before it resumes;
- authoritative online verification MUST require the token epoch to equal the current Agent epoch;
- lifecycle state, events, evidence, and outbox SHOULD be committed in the same transaction.

### 6.3 Instance State

An Instance MUST support at least `bound`, `active`, `expired`, and `terminated`. A terminated or lease-expired Instance MUST NOT obtain a new token.

Instance termination MUST cause already-issued tokens to become inactive at the next authoritative online verification. Offline verification cannot provide this guarantee; blocking only new issuance is not equivalent to immediate revocation. Credential generation and token issuance are specified in Part 3.

## 7. Registry

### 7.1 Registration Transaction

Registration MUST:

- validate the caller's authority to create an Agent under the target Authority Namespace;
- assign a local Agent ID unique within the Namespace;
- create an immutable Authority Binding;
- persist a specific, explicit Blueprint version, if used;
- record registration evidence;
- commit the Agent record, the Authority Binding, and the evidence in the same transaction.

### 7.2 Uniqueness and Namespace Integrity

- `namespace + agent_id` MUST be unique within the registry;
- a namespace MUST NOT be reassigned to a different principal;
- cross-namespace queries MUST NOT assume that a bare `agent_id` is unique;
- tenant-like deployment partitions, if retained internally by an implementation, MUST NOT appear as interoperable claims.

### 7.3 Management Plane

Registration, Blueprint, Workload Registration, trust-domain, and namespace delegation APIs MUST be strongly authenticated and finely authorized, and MUST produce security events. Merely relying on network location or a shared internal token is insufficient for a high-assurance management plane.

## 8. Discovery

### 8.1 Goals

Discovery resolves trusted metadata without relying on caller-supplied hints:

- Authority Namespace → issuer metadata and registry endpoint;
- Agent Identifier → the identity authority that owns it;
- issuer → verification keys (JWKS) and trust bundles;
- Federation Trust → peer metadata (see Part 5).

Discovery concerns identity and registration only. Capability, tool, and business-resource discovery is out of scope.

### 8.2 Discovery Document

An Authority Namespace SHOULD publish a discovery document at a well-known HTTPS location under the namespace, for example `https://<namespace-host>/.well-known/agent-iam`. The document MUST be retrieved over HTTPS and MUST contain at least:

```text
discovery_version
namespace                      # canonical Authority Namespace
issuer                         # canonical issuer identifier
registry_endpoint              # optional; registration/management API
jwks_uri                       # verification keys
supported_proof_profiles
supported_artifact_types
conformance_claim_ref          # optional
key_rotation                   # overlap and propagation metadata
```

The document SHOULD be signed. When signed, the signature key MUST be resolvable independently of the document itself, and key rotation MUST preserve verification of previously issued artifacts for at least the maximum artifact lifetime plus clock skew.

### 8.3 Resolution Rules

- The namespace used for resolution MUST be canonical (Section 4.3) and MUST be compared by exact string, not by URI normalization;
- an issuer resolved from a document MUST be registered and MUST NOT be accepted as authoritative merely because it is self-declared;
- results MUST be cached with a bounded maximum age; stale metadata MUST fail closed for new issuance and MUST NOT be used to satisfy revocation;
- unknown or missing metadata MUST fail closed.

### 8.4 Discovery Security

Discovery retrieval is a network-facing trust operation and MUST:

- be restricted to HTTPS, except for an explicit local development exception;
- enforce host and scheme allowlists, DNS/IP re-validation, redirect limits, response size limits, connection and read timeouts, and content-type checks;
- reject loopback, link-local, cloud metadata addresses, and unapproved private network targets to prevent SSRF;
- rate-limit refreshes triggered by unknown `kid` or repeated failures;
- bound the maximum usable time of stale keys.

Part 5 defines the corresponding constraints for peer and federation metadata retrieval.

### 8.5 Binding to Identifiers

- a discovered issuer MUST map to exactly one canonical Authority Namespace in the deploying trust domain;
- an Agent Identifier MUST be resolvable to its owning registry only through its Authority Namespace;
- if a network URI representation of an Agent is used, it MUST be derived from the canonical namespace representation and MUST NOT introduce a new, unregistered scheme.

## 9. Security Considerations

- Registration and namespace delegation are high-value management operations and MUST be strongly authorized (Section 7.3).
- Discovery introduces an additional attack surface; Section 8.4 constraints are mandatory.
- Lifecycle epoch monotonicity and terminal revocation (Section 6.2) are required to prevent credential and authorization reuse.
- External identifiers (Section 4.6) MUST NOT override local identity.

## 10. Privacy Considerations

- Agent IDs SHOULD be opaque and carry no personal data (Section 4.2).
- Discovery documents SHOULD expose the minimum metadata necessary for interoperation and SHOULD NOT enumerate Agents.
- Namespace hierarchies may reveal organizational relationships; cross-domain disclosure SHOULD be minimized per Part 1 Section 7.2.

## 11. Conformance

A Part 2 conformance claim MUST state:

- supported namespace canonicalization form;
- the discovery mechanism(s) supported and their caching bounds;
- whether signed discovery documents are supported;
- the registry transaction and management-plane guarantees;
- known extensions and unmet clauses.
